This continues [Your First Application](@/docs/getting-started/first-application.md). A workspace is useful when packages are developed together; it also gives you a way to freeze runnable targets into a packed workspace. Start with one member so you can see the parts before adding more.

## Make the workspace

In the `counter` folder, next to `jess.toml`, create `jess-workspace.toml`:

```toml
manifest_version = 1

[workspace]
members = ["."]
```

The dot means the package at the workspace root. From `counter`, ask what Jess found:

```sh
jess workspace info
jess workspace targets
```

The first command lists `com.example.counter`, its target, dependencies, and lock state. The second lists `com.example.counter:counter`, an application target and the default. This example has no external dependencies, so it has no packages to pin and no lock file yet.

Run it through the workspace:

```sh
jess workspace run counter
```

It prints the same entry, startup, and shutdown messages as `jess package run`. The workspace did not change the package or its lifecycle.

## Pack it

Still inside `counter`, write a packed workspace beside the folder:

```sh
jess workspace pack --output ../counter.jsw
```

The report identifies the output, its hash, the default target, and the packages it contains. From the parent folder, run it:

```sh
jess counter.jsw
```

It prints the same three lines. The `.jsw` contains the frozen target and packages it needs; it does not read the source workspace or sync dependencies when run. Editing the source afterwards does not edit the artifact: pack it again to distribute the change.

## Grow it

Add another Package Source under the workspace root and name its folder in `members`. A member that uses another package still declares that dependency in its own manifest. When external packages are needed, `jess workspace sync` resolves them and writes `jess.lock`; commit the workspace file and lock so other developers can reproduce the selection. The kept JPKs under `.jess/packages` are regenerated by sync.

The [workspace reference](@/docs/cli/workspace.md) covers dependency sources, offline operation, target selection, and standalone executables. A `.jsw` needs a compatible Jess runtime; the standalone form combines it with a runtime for a specific platform.
