The [render graph](@/docs/contributing/render-graph.md) says what to draw in what order, and the [shader IR](@/docs/contributing/shader-ir.md) says how each draw shades. Something has to own the hardware they run on. `jess::gpu` (`src/gpu`) is that: one adapter, the device opened on it, the bytes and images on that device, and the pipelines and passes that draw with them.

## What It Is

- **A device.** `Gpu::headless()` takes whatever adapter the machine has, preferring a hardware one and falling back to a software one, and opens a device on it. It looks through Vulkan, Metal, and Direct3D 12 first and OpenGL only when none of them answers (`WGPU_BACKEND` overrides both), and every device in the process opens through the same two wgpu instances, one at a time: the Vulkan loader crashes when instances come and go on several threads at once, and OpenGL's contexts belong to the thread that made them. `Gpu::info()` reports the adapter's name, the API it's reached through (`vulkan`, `metal`, `dx12`, `gl`), what kind of device it is, and the limits a caller sizes things by.
- **Buffers.** Bytes on the GPU, bound as any of vertex, index, uniform, and storage buffers, written from the CPU and read back. Sizes, offsets, and lengths are whole 4-byte words, which is what the GPU copies.
- **Commits.** `Gpu::defer` queues a change for the next `Gpu::commit`, which applies every queued change in order under the device's frame lock; whatever records a frame on another thread holds that lock while it records, so it draws a commit's changes whole or none of them. The queue holds `CHANGES` changes carrying `BYTES` bytes, and refuses one past that (`Gpu::room` says how much fits). `write_buffer_later` and `write_texture_later` check a write now and apply it at the commit; the Luau binding makes every change a script makes this way, and commits before anything that waits on the GPU. `Gpu::commits` counts the commits that applied anything. The rest of `jess::gpu` applies at once: the deferring is for whoever shares a device with a frame drawn elsewhere.
- **Reads.** `Gpu::read_buffer_later` and `Gpu::read_texture_later` copy bytes back without waiting: a `PendingRead` that `poll` checks without blocking and `wait` waits for, unpadding a texture's rows once they're there. `read_buffer` and `read_texture` are the same, waited for.
- **Textures.** 2D, layered, cube, and 3D images in a [`TextureFormat`](@/docs/contributing/render-graph.md#targets), with mip levels, sampled by shaders, drawn into as targets, or both. A level of a layer is written from tightly packed rows and read back the same way; jess pads and unpads the rows the GPU's copies need. A multisampled texture (`samples: 4`) is a 2D target of one level, drawn into and resolved, never sampled, copied, or read back. Each texture keeps a 2D view of each level of each layer once something asks for it, so drawing into a level or binding one makes no view per frame.
- **Samplers.** Nearest or linear filtering, between texels and between mip levels, clamping, repeating, or mirroring past the edges, and an optional comparison for depth textures.
- **Pipelines.** `Gpu::render_pipeline(program, state)` takes a [shader program](@/docs/contributing/shader-ir.md) and its fixed-function state (topology, culling, which way round faces the camera, a color target per fragment output, and an optional depth test) and builds everything else from the program's own layout: a bind group layout per frequency, the vertex buffer layouts per rate, a matrix attribute as a column per location. The state's color targets must fit the outputs: a `UInt` output needs an unsigned integer target, and a target can't have more channels than its output. `Gpu::cached_render_pipeline` and `Gpu::cached_compute_pipeline` share pipelines: a program that lowers to the same WGSL, with the same state, gets the one already compiled while anything holds it (the cache holds them weakly), and `Gpu::pipeline_stats` counts what was compiled and what reused. Lowering is deterministic and the WGSL carries every binding and attribute the layouts come from, so the WGSL is the key.
- **Bind groups.** `Gpu::bind_group(pipeline, frequency, bindings)` binds exactly what the program declares for that frequency, each binding checked against its declaration: a uniform buffer at least as large as the block, a texture of the declared shape and of a format the declaration reads, a comparison sampler where one is declared. A group binds for every pipeline whose program lays that frequency out the same way, whichever pipeline it was made for: the device makes one layout per distinct arrangement of bindings and shares it, so a camera block made once binds for every program that declares it alike.
- **Compute.** `Gpu::compute_pipeline(program)` takes a compute program the same way, `Gpu::compute_bind_group` binds for it, and `Gpu::dispatch(pipeline, groups, workgroups)` runs it over a grid of workgroups, each of the size the program declares.
- **Passes.** `Gpu::render(colors, depth, draws)` draws into a level of a layer of each target, starting from a clear or what the target held, with the render graph's own `LoadOp`, `StoreOp`, and `ClearValue`; a multisampled color target can resolve (`Target::resolve`) into a level of a layer of a single-sample texture of its format and size, and a pipeline drawing into multisampled targets says so (`PipelineState::multisampled`). Each draw is checked before anything is recorded: its pipeline's targets are the pass's, it has a bind group for every frequency its program binds and none for the rest, its buffers are vertex and index buffers, and its count stays inside them. An indirect draw (`Draw::indirect`) takes its counts from a buffer the GPU wrote, a compute pass's count of the instances it kept, say, so only its argument buffer's usage and size are checked; with storage atomics, that's GPU culling with no count ever coming back to the CPU.
- **Draw sets.** A `DrawSet` is a draw kept: a pipeline, its material and draw bind groups, its buffers, a count and an instance count, and the tags the passes that take it look for. Its pass group is the pass's: `set.draw(pass)` is the draw it is now under a pass group, so one camera block serves every set a pass draws. It is checked once, when it is made, the way a pass checks a draw; afterwards its count, instance count, and visibility change through atomics, checked again as they change, so whatever draws a frame never waits on whatever changes one. `DrawSets` holds them in the order they were added, and `DrawSets::matching(tags)` is the visible ones carrying any of `tags`, in that order. Its `version` counts every addition and removal, for whatever caches a choice.
- **Plans.** `Gpu::plan(graph, work, viewport)` compiles a [render graph](@/docs/contributing/render-graph.md) for the device, with one `Work` per pass saying what it does, and `Gpu::run(plan, sets, imports)` runs every pass that survived, in order, in one submission. Planning allocates one texture or buffer per alias group, sized for the viewport, and makes every bind group it can; running records the passes and nothing else. Details below.

## Plans

A render graph says what each pass reads and writes. A plan adds what each pass does, as one `Work` per pass in the order they were registered, and the kind has to match the pass's:

| Pass | Work | Records |
| --- | --- | --- |
| `Mesh` | `Draw { tags, pipeline, pass }` | the visible draw sets carrying any of `tags`, in the order they were added, each with `pass` as its pass group |
| `Fullscreen` | `Fullscreen { pipeline, groups }` | three vertices of `pipeline`, no buffers: a triangle over the targets |
| `Compute` | `Compute { pipeline, groups, workgroups }` | a dispatch of `pipeline` |
| `Copy` | `Copy` | the pass's source into its destination, the region the graph's copy pass names |

A pass's targets are its writes, each at the level of the layer it names and resolving where it says so, and its depth test, if it reads one: a `DepthTest` read is the pass's depth attachment, read-only, so a set whose pipeline writes depth there is refused. A fullscreen pipeline's targets and sample count are checked against its pass's when the plan is made. A buffer written with `Clear(Zero)` is zeroed first, at every run.

Each kept resource gets an allocation of its own, made with the plan and zeroed, which `Gpu::read_kept` and `Gpu::read_kept_later` read back; a resized plan's start zeroed again. A buffer sized by the viewport is allocated at the plan's, and `Plan::buffer_bytes` and `Plan::target_extent` say how big a resource is there, for the host sizing an import.

A target is allocated as the graph describes it: a 2D texture, or a 2D array where it has several layers, with its levels and samples. A relative target is sized by `TargetDesc::resolve`, which never leaves its levels without pixels, and so is an imported one.

A group is either one made already (`PlanGroup::Bound`), or bindings the plan makes into one (`PlanGroup::Make`) for the pass's pipeline, or for a draw pass the `pipeline` its work names. Bindings can name the graph's own resources: `PlanBinding::Target` binds a target the pass reads as a texture (all of it, or as a 2D texture the one level of one layer the pass reads, `Binding::Level`), and `PlanBinding::Buffer` binds a buffer as a storage buffer, which the pass has to read for a read-only declaration and write for a read-write one. Groups are made when the plan is, except those that bind an imported resource, which are made at every run, because the import is the run's.

A copy is resolved to offsets and extents (`RenderGraph::resolve_copy`) when the plan is made, at its viewport, so a region of a relative target that doesn't fit fails then, and a run records it as it is. A copy between a target and a buffer lays each row out as its texels padded to a multiple of 256 bytes, the layout the GPU copies in, and the buffer has to hold every row from its offset. Nothing writes a depth target from a buffer.

Between runs a plan changes only through its controls, shared by the plan and every plan `Plan::resized` makes from it, so a window showing it at its own size follows along: `Plan::set_enabled` leaves passes out of later runs or puts them back, refusing a change after which a recorded pass would read or load what a left-out pass stores, and `Plan::set_region` changes what a copy pass copies, checked at once and resolved again at each plan's own viewport.

A run makes nothing the run before it made. Targets are drawn into and read through the views each texture keeps of its levels, a draw pass keeps the sets it chose from a collection until the collection's version changes (adding or removing, not showing or hiding), and a group that binds an imported resource is made again only when a run gives a different texture or buffer than the last, by identity. `Gpu::made` counts every object ever made, so a test can hold a run to it.

`Gpu::run` takes the draw sets its draw passes choose from, and an `Import` for each imported target and buffer: a texture of the declared format and size at the plan's viewport and of its levels, layers, and samples, a buffer of the declared size. `Plan::resized(viewport)` is the same plan for another viewport, its transient targets and the groups that bind them made again. `Plan::order()` names the passes that run, and `Plan::allocations()` counts what the plan allocated.

On a device whose adapter offers timestamp queries (`GpuInfo::timestamps`, requested when the device opens), a plan times every drawing and compute pass: a query pair per pass written at its start and end, resolved into a buffer at the end of each run. `Gpu::timings(plan)` reads the last run's back as a `PassTiming` per pass, in nanoseconds converted by the queue's timestamp period. Copies aren't timed: timing one would need timestamps inside an encoder, which isn't portable.

## Generations and Teardown

Every buffer, texture, sampler, bind group, and pipeline holds a token of its device's `LiveCounts`, given back when it drops; `Gpu::live` reads them. wgpu keeps an object the GPU is still using until it is done with it, so dropping one is always safe, whatever is in flight.

A script domain's generations share one device through `jess::lua::SharedDevice`, a service an application's host gives its domain: the first `jess.gpu.device()` opens it and every later generation's gets it again. A generation's handles live in its runtime, so they go when it does, draw sets and plans with them, and its successor can't name them. The test that restarts an application on a GPU checks exactly that: the same device after the restart, and none of the old generation's objects alive on it.

## Windows

`jess::window` (`src/window`, feature `window`, which brings `gpu`) opens native windows through winit, each with a `Surface` made on the device's own wgpu instance from the window's handle. A surface's next image is a `SurfaceFrame` whose texture is an ordinary jess `Texture`, so a window is drawn the way anything is: as the imported target of a plan. `Window::show` keeps a plan, a `SharedPlan` the script holds too, which the window replaces with the plan resized whenever it is resized, so every holder runs and reads the plan the window draws; a plan is shown in one window at a time. `Window::show_later` and `hide_later` do the same at the device's next commit, which is how Luau shows one.

Windows draw on the presenter, a thread of `src/window/presenter.rs` that owns nothing but the shared `Screen` of each window (its surface, device, plan, and the commit it last drew). It draws a window when its device committed changes since, or it was shown a plan or resized, recording under the device's frame lock so it draws a commit whole, then presents outside it; a window whose image isn't ready is tried again a few milliseconds later. A draw that fails presents nothing and counts no frame: the image goes back to the surface unshown, the failure is reported once however long it lasts, and the window is tried again every tenth of a second until it draws. A surface that is lost, as when the display changes or the driver restarts, is made again on its window (`Surface` keeps a handle on it) at the next try, and again at each try after until it comes back. `window::present` ends a frame: it commits each window's device, reports what the presenter or a resize failed at, and wakes the presenter, without waiting. `window::wait_presented` waits for it, which is how `jess.gpu.pump` paces a script's own loop. Locks go one way: a window's screen, then what a commit shows on it, then the device's frame lock; a commit takes the frame lock and then what it shows, never a screen. `Window::frames` counts what a window presented. An application's host posts the named event `window::NEWS` (`jess.window`) for each window `window::news` reports, one whose events nobody has read or heard of, so an application learns of a resize without running anything per frame.

winit allows one event loop a process, on the thread that made it. Jess makes it at the first window (a first try that fails, without a display say, claims nothing, and the next window tries again) and pumps it without blocking (`window::pump`) from whatever drives the frames: an application's host pumps before each frame and presents after it, so the host stays the application's one loop, windowed or headless. Keyboard and pointer events go into a bounded queue that `WindowInput`, an input `Backend`, drains into the host's input service at the host's clock, or a script's headless input runtime at its own when it asks for its windows; with nobody listening, nothing is kept. What happens to a window itself (resizes, scale, focus, close requests, closing) goes into the window's own bounded list of `WindowEvent`s, which `Window::events` drains; a window opened with `closes: false` only reports a close request.

A window opened with a `key` is held by the window system, not only by its handles. `window::reclaim(load)` runs a load (an application's restart does) and closes, after a successful one, the kept windows the load didn't open again; opening a kept key hands the window back, its surface made again on the claiming device if it is another. Between generations a kept window keeps its last plan, whose GPU objects the window holds, so the person sees the last frame of the old code until the new code shows its own. `window::release` closes them all when the application stops.

winit is taken with X11 and Wayland, loaded at run time, and Wayland's client-side decorations without a title, which keeps a font stack out of the build. Everything it brings is MIT, Apache-2.0, BSD, or Zlib.

The window test opens a real window, so it runs only with `JESS_WINDOW_TESTS` set, on a desktop.

## What It Is Not

- **Not a wgpu wrapper.** No public type names a wgpu type. Usages are jess's own small sets, formats are jess's list, and errors are jess's.
- **Not a renderer.** It doesn't know what a mesh, a camera, or a material is. What a buffer holds and why is the caller's business, and in the end Luau's.
- **Not required.** It's behind the `gpu` feature, and windows behind `window`. Both are on by default, so a release has them, and both load the platform's GPU API and window system at run time, so a jess on a machine without either still starts. `--no-default-features` builds the kernel without a GPU stack or a window system at all.

## Why wgpu

wgpu is the one GPU API that reaches Vulkan, Metal, Direct3D 12, and OpenGL from one Rust interface, validates what it's given instead of crashing the driver, and speaks WGSL, which is what the shader IR lowers to. jess takes wgpu 30 with only the native backends (`vulkan`, `gles`, `metal`, `dx12`) and `wgsl`, and pollster to wait on its futures. Both, and everything they pull in, are MIT, Apache-2.0, Zlib, ISC, or BSD-2-Clause; the native pieces (the Vulkan loader, GL and EGL, Metal, Direct3D) are the system's own, loaded when the device opens.

## Errors

A call that can fail checks its arguments in jess's terms first: a buffer of 6 bytes, a cube with oblong faces, a level a texture doesn't have, bytes that don't fill the level they're for, a `Vec4f` output drawn into an `R32Uint` target, a draw without the material bind group its program needs. Each is a `GpuError::Invalid` naming what's wrong and what was expected. What gets past that runs inside a wgpu error scope, so anything wgpu refuses comes back as `GpuError::Backend` with wgpu's message, rather than through wgpu's default handler, which panics.

## Testing

The tests are in `tests/gpu`, behind the feature, which is on by default: `cargo test --test integration -- gpu::`. Each runs on whatever adapter the machine has, a software one (lavapipe, llvmpipe, WARP) included, and skips with a `SKIPPED` line on a machine without one.
